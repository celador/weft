0:26-0:58 · Slide 2: the numbers

"On October 3rd, a Saturday night, I read Cloudflare's post about the next Git platform, and I started asking questions. Eighty minutes later, the first commit landed. Sixty-four hours after that, I submitted. 231 files. 38,593 lines. Every commit was written by an agent. And in the first eleven hours alone, Weft's log recorded 627 events and 460 edits. 59 times, Weft told one agent to wait for another."

0:58-1:47 · Slide 3: the product

"This is Weft. It's a live feed of every edit every agent makes to a repo, in order, as it happens. Not after the merge. While they type. Every row is one event: which agent, which file, what it was doing, and which task on the board it was for. On the right are the squiggles: the edits that would have broken someone else's work. Each one names the function, the file, and the event that caused it. And it tells the agent what to do next: read the new version, and update your call. It's public and read-only. You can watch it from your seat."

1:47-3:35 · Slides 4-5: how it works

"Here's how it works. Every time an agent edits a file, that edit goes through a checkpoint for the repo. Cloudflare runs exactly one copy of it, a Durable Object, so every agent sees the same history. The real question isn't which edit came first. It's which change breaks which. If one agent changes a function and another still calls the old version, the healthy order is: the second agent adopts the new signature, then it lands. So an edit that relies on something another agent just changed doesn't land. The agent gets a squiggle back, inside its own run: this function changed, here is the change. It fixes its code and tries again. And main moves one checked landing at a time. Under the hood: Workers serve the API and the site. A Durable Object per repo keeps the order. Artifacts stores the git. Workflows and Queues land the work on main. And the rules are an open protocol, WCP. It's a draft, version 0.1, and it can run anywhere. Weft plugs in where the agents already are. Claude Code, Codex and OpenCode can all run a hook on every tool call, and that's where the check happens. In our test runs, eighteen agents across those three tools worked on one repo at the same time, through one checkpoint. A typical check takes just over half a second, so the agent barely notices."

3:35-3:57 · Slide 6a: without Weft (22 seconds, muted, a real recorded run, narrate over it)

"First, the same two agents with Weft switched off. One changes createSession. The other keeps calling the old version. Each branch passes its own tests. Git merges both, no conflict. Then the build breaks on main, and someone has to send the work back."

3:57-4:44 · Slide 6b: with Weft (47 seconds, muted, narrate over it)

"Now with Weft. Claude Code on the left, Codex on the right. Claude Code changes a function called createSession. Now Codex tries to edit code that calls it. Refused. There's the squiggle. Codex reads the error, it's told exactly what changed. It adapts its code. It tries again, and it's accepted. No human stepped in. No merge conflict. Nobody found out at review time."

4:44-5:15 · Slide 7: how it was built

"That's not only a demo. Weft coordinated the agents building Weft. By Monday its log had 918 events, 679 edits and 27 landings on main. Sixty waits. Five edits refused before they could land. Event 834 is a real one: refused because event 813 changed a type it used. The next try was accepted. And this is how I work with agents: explore, decide, delegate, verify, repeat."

5:15-6:22 · Slide 8: why it matters

"Why does this matter? One agent is a tool. Ten agents on one repo is a team, and teams step on each other. Today they find out at merge time, like the first clip. Weft moves that moment to edit time, where the fix is cheap: the agent is still holding the task. In two weeks: 39 stars, a stranger filed 22 issues and pull requests, and the Beads team asked how to integrate. It's a prototype. It understands TypeScript and JavaScript today. Nobody runs it in production yet. Next: a Time Machine for agent work. Weft already renders a preview of every revision. The timeline to scrub through them and jump to the one that broke it isn't built yet. With the credits, I'd run a free hosted coordinator for outside teams, and a public benchmark with and without Weft, measuring the rework it saves."

6:22-6:27 · Slide 9: thesis

"So that's Weft. Red squiggles, for teams of coding agents."

6:27-6:44 · Slide 10: takeaway

"We have to assume the code editor disappears. If it does, agents still need squiggles. It's live right now at weft.elier.ai. Scan it, watch the agents. And I'm looking for my next builder role. Thank you."

Top questions

Top 8 judge questions

Say the answer, then stop. Full list with sources: ../qa.md.

1. Did you write the code?
No. Agents wrote it, coordinated by Weft itself. I designed it in one conversation on Oct 3, then made the decisions and kept final sign-off.

2. Did a human review the code?
Not line by line. I reviewed evidence instead: tests, a recorded demo and Weft's public log, and I signed off on anything public.

The scale is why. From my first message to the submitted entry took 64 hours (Sat Oct 3, 10:00 PM to Mon Oct 6, 1:40 PM). In that time the agents wrote 231 files: 38,593 lines of code and tests, about 2 million characters. The usual industry figure for a human is 10 to 50 finished lines a day (Steve McConnell, Code Complete). At 50 a day, writing it by hand would have taken me about 770 working days, roughly three years. Even at the best small-project rate McConnell reports, 125 a day, it's over a year. Today the repo has about 44,000 agent-written lines in roughly 270 files, plus about 1,400 lines from an outside contributor.

Lines of code aren't a measure of quality. They show why line-by-line review stops working, and why the checks have to happen while the agents are writing.

3. How is this different from git merge or a merge queue?
Git and merge queues find conflicts after the code is written. Weft checks each edit while it is being made, at the level of functions and types, so the agent hears about it before a commit exists.

4. Why Cloudflare?
Weft has three layers, and Cloudflare matters for two of them.

The protocol (WCP) is an idea, not a Cloudflare product. It's a written set of rules for how agents report edits and get back allow, advise or deny. It can be built on other technology and run locally. The repo ships a reference coordinator that runs with no Cloudflare at all, and a full local server is in progress.

The platform and the product are where Cloudflare earns its place. Running this for real takes a lot of infrastructure, and Cloudflare has all of it in one place:

  • one ordered log per repo: a Durable Object, one per repo with its own database, so I didn't build leader election or run a database cluster
  • git storage for main and every candidate change: Artifacts
  • background jobs that test, pick, land or revert: Workflows and Queues
  • a safe place to run git and tests: Sandbox containers
  • the API, web app and previews: Workers, plus D1 and R2 for the index and logs

Short version: the protocol runs anywhere. Cloudflare is what lets the platform and product run at scale, close to every agent, without me operating servers.

5. What do you use Artifacts for?
Each repo's main branch lives in Artifacts, and every agent attempt gets its own fork with a repo-scoped token. Push events from the forks come back into Weft's log.

6. Who uses it?
Weft's own build, and my own agents across my repos. No outside team runs it in production yet; that's the next step.

7. What breaks today?
The code analysis is TypeScript and JavaScript only. If the coordinator is down, agents keep working unchecked, and the fully local mode isn't merged yet.

8. What would you do with the $25k in credits?
Run a free hosted coordinator for outside teams, and a public benchmark: many agents on real repos, with and without Weft, measuring the rework it saves.

If asked about speed: a check takes a median 558 ms (demo/evidence/m1-report.md); agents spend seconds per turn.

Deep questions (Git panel)

Say the answer, then stop. Sources per answer: review/deep-qa.md.

1. How does conflict detection work, exactly?
When an agent starts a change, it gets the log position it started from, its "base". Every edit it sends says what it changed and which functions and types it relied on, its read set. The coordinator looks only at what other changes wrote after that base. If one of them landed a write to the same function, the edit is rejected as a stale overwrite. If one changed the signature of something you read, or deleted it, the edit is rejected too. A body-only change to something you read is just a warning. It's the same idea as optimistic concurrency in a database: check against what changed since you read, don't lock.

2. And when two agents are editing the same thing at the same time, before either lands?
Agents can claim a function for a short time, like a lease. If two claims collide, the more senior change wins: higher task priority first, then whoever started first. The default rule is wound-wait: a senior agent proceeds and the junior one is told to back off; the alternative is wait-die. Exactly one side is told to adapt, and the ordering never changes, so they can't deadlock or keep backing off from each other. By default this is advice, a warning; a repo can switch to "block" so the losing edit is refused.

3. The sequencer is one Durable Object per repo. Isn't that a bottleneck, and what if it goes down?
Yes, by design: one object per repo is what gives a single, ordered log, the way a database primary does. Repos don't share anything, so a thousand repos are a thousand independent objects. The log is in that object's own SQLite storage, so if it restarts, Cloudflare brings it back with its data. While it's unreachable, the adapters fail open: the agent keeps working unchecked and the miss is logged. That's a deliberate choice, and an honest gap if you need strict guarantees.

4. How much latency does it add per edit?
A pre-edit check measured a median of 558 ms, 753 ms worst case, against the deployed gateway. Most of that is the round trip from the laptop to Cloudflare; the check itself is a few small SQL reads. Agents spend seconds on each model turn, so it's a small slice. In "advise" repos the edit isn't held at all; it's reported in the background.

5. How does it scale to many agents and many repos?
Repos scale out, since each repo is its own object. Per repo, the ceiling is how many checks one object can handle per second, and I haven't load-tested that ceiling. The largest real run was 18 live agents on one repo, and my own setup reports edits from 8 agent profiles across 50 repos. A load test is the first thing the credits would pay for.

6. What about false positives?
The main source is coarseness. For TypeScript and JavaScript the analysis is per function and per type. For other languages, and for files the parser can't read, it falls back to the whole file, so two agents in different parts of one Python file will get a warning. Body-only changes are warnings, never blocks, and only signature or delete changes to things you actually read are errors. I don't have a measured false-positive rate yet.

7. Why not file locks, git worktrees or CRDTs?
Locks make agents wait and they're too coarse, since two agents in one file is usually fine. Worktrees we do use, one per agent, but they only isolate. They hide the conflict until merge time, and Weft is what tells them about each other. CRDTs merge text automatically, but here the danger is the opposite: two edits that merge cleanly as text and still break the build, like calling a function whose signature just changed. We want that conflict reported, not merged away.

8. How do agents hook in? Which ones work today?
Each coding agent has hooks that run before and after a tool call. Our adapter is a small program those hooks call: before an edit it asks the coordinator, and if the answer is reject, the agent sees the reason and adjusts. Live today: Claude Code, Codex, OpenCode and Hermes. Cursor CLI and Gemini CLI adapters are tested against their documented formats only, and there's a file-watcher for tools with no hooks.

9. How do security and auth work?
Every agent gets its own token, scoped to one repo and bound to that agent's id. It can't act as another agent or touch another repo; a wrong repo just looks like "not found". Tokens are stored only as SHA-256 hashes and shown once when issued. Read-only observer tokens are separate. The containers that run git and tests hold no secrets. What's missing is self-serve token issuance and any SSO; today the operator mints tokens.

10. What's actually live, and what's a prototype?
Live: the coordinator and gateway on Cloudflare, the adapters for my own agents across my repos, and the public read-only web UI at weft.elier.ai. The rebase, test and land pipeline on Artifacts, Workflows and Containers ran in the demo runs, but it needs real Cloudflare setup and no outside team runs it. Not built yet or not merged: analysis for languages other than TypeScript, and the fully local mode, which is on a branch.

11. What does it cost to run on Cloudflare?
I haven't measured cost per repo, so I won't give a number. Development ran on the $5-a-month Workers Paid plan. An idle repo is just stored data in its object, so it costs almost nothing. The real costs are container minutes for rebases and tests and model calls for reviews, and they grow with how much work lands, not with how many agents are connected.

12. What does WCP standardize, what's Weft-specific, and what's next?
WCP is the wire protocol: the event format, the conflict rules, the arbitration rules and auth scopes, so any agent and any coordinator can interoperate. Weft is one implementation on Cloudflare, plus the analyzer, adapters, web UI and land pipeline. We proposed the hook layer to the Agentic AI Foundation as a discussion item; it's a draft, not a standard. Next is a second implementation that isn't on Cloudflare, and working with tools like Beads that already track agent tasks: Beads decides what each agent works on, Weft checks the edits as they happen. There's no Beads integration yet.
